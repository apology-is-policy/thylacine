## Prosecution

The #104 root fix masked IRQs before reading the per-CPU pointer in
`sched()`. The audit found `ready_on` doing the same unguarded thing:
reading `smp_cpu_idx_self()` — and deciding `target_cpu == self`, and
therefore which CPU's tree to enqueue on and which CPU to poke — before
masking.

A migration between the read and the run-queue-lock acquire enqueues the
thread onto, and pokes, the **wrong CPU's** slot.

## Why it was fixed rather than documented

This is the disposition worth keeping. It was **sound at the time**:
every live caller already masked — `wakeup` holds the timer-wait lock
irqsave, the SVC spawners are hardware-masked — so a comment stating the
precondition would have been true and would have made the code look
audited.

It was fixed anyway, by masking first inside `ready_on`, on the explicit
reasoning that an **unstated caller precondition is not a defense**: the
first IRQ-enabled kthread caller would reintroduce the bug silently, and
nothing in `ready_on`'s signature would have warned them. Masking first
closes the *class*.

Which is the same judgement as [[fnd-866-r1-f2]] and
[[chg-2026-05-31-801-steal-claim]], and it recurs on this surface for a
reason: SMP bugs here are not found by the tests, so "unreachable today"
buys nothing — the thing that makes them reachable is a new caller, and a
new caller is not a code change anyone reviews as a scheduler change.

## Context

The parent bug (#104) had already been "fixed" once on a wrong theory —
a hypothesized mid-handler steal, closed by removing the syscall-return
preempt, which merely lowered migration churn below the rate that hit the
window. A week ran green. It was root-caused red-handed only by a
temporary in-kernel assertion that printed `cs_idx=0 running_cpu=1`.
