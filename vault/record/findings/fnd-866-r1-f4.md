## Prosecution

The pre-#864 `ready()` reached its per-CPU slot through
`this_cpu_sched()`, which extincts cleanly on an out-of-range index. The
split into policy plus mechanism replaced that with a direct
`smp_cpu_idx_self()` read in `ready_on` — and the new code guarded only
the **target**, via the fall-back-to-self path.

So a bad *self* index produced an out-of-bounds `g_cpu_sched[]` access
rather than a clean failure. The fallback made it worse in a small way:
an out-of-range target falls back to `self`, which is exactly the value
that was never checked.

## Fix

Restore the guard: `if (self >= DTB_MAX_CPUS) extinction(...)`, before
any array access.

## Why a refactor lost it

Worth recording as a shape rather than a bug. `this_cpu_sched()` carried
the check *as a side effect* of being the accessor. Inlining the index
read to make the CPU explicit — which the policy/mechanism split needed —
silently dropped it, because nothing in the new expression looks like it
used to be checked.

The general form: when a helper is replaced by its body, the helper's
guards are the part most likely to be left behind, because the body reads
as complete without them.
