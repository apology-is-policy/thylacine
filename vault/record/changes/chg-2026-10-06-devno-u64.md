The kernel's device number (`spoor_next_devno`) was a monotonic `u32` that
wrapped with no refusal. Every Env and every dev9p / devsrv attach mints one, so
an unprivileged fork loop drives it, and three identity keys assume a live
instance's number is unique: the mount key and `MNOEXEC` coverage
([[sub-kernel-territory]]) and the Image cache key ([[sub-kernel-image]]), where
an alias would serve one instance's cached pages for another instance's file.
The number is now 64 bits end to end ([[sub-kernel-spoor]]: the Spoor, the Env
([[sub-kernel-content]]), the mount entry, `struct mkey`, the shed's instance
set, the Image cache entry and the FILE Burrow's key ([[sub-kernel-burrow]])),
never reused, and each key copy is pinned to the Spoor field's width by a
`_Static_assert`. The mount entry keeps its 40 bytes by reordering.

By the operator's vote [[dec-2026-09-28-t-stat-devno-u64]], `t_stat.devno` is
widened in place over `_pad_dev` ([[abi-t-stat]]): offset 80 and the 88-byte
size are unchanged, the kernel adds a width assertion, and the six mirrors that
name the field change in the same commit. Two stale "80 bytes" comments in
those mirrors, recorded by [[abi-t-stat]], are corrected with them.

**Built eight days later, on a moved tree.** The WIP of 2026-09-28 was rebased
onto main after the multi-client Loom chunk. A consumer it predated (the
served-link anchor check in stalk) compares Spoor fields and needed nothing.
Two tests stamped values below 2^32 and so could not tell a 64-bit path from a
32-bit one; they now carry values above it. The build does not warn on a
narrowing, so a `-Wshorten-64-to-32` pass over all 224 kernel translation units
was compared with the base: no new narrowing, and a control proves the pass
catches a devno narrowed on this tree and not on the base.

**The maps device column** ([[sub-diorama]]). diorama rendered
`/proc/<pid>/maps` as `00:<devno>`, while vivarium reports `st_dev = devno`, so
for any devno of 256 or more a Linux reader comparing `makedev(maj, min)` with
`st_dev` disagreed (pre-existing since #100). The column is now the glibc/musl
split of the devno, which is `makedev`'s inverse over all 64 bits, as Linux
shows the MAJOR:MINOR of the device whose encoding stat returns.

**The audit.** Round 1 (Fable 5.1): 0 P0 / 0 P1 / 1 P2 / 5 P3. The P2: the new
full-width mount test mounted `('-', 1, qid 0)` on itself, which the I-3 cycle
check refuses, so the test would have stopped at its first assert and the
widened mount key had no runtime witness. Its fix gave the source its own qid,
and two legs now witness the stored mount key and the cycle check's key at
run time, where only `_Static_assert`s had. The P3s: two pouch comments still
said `st_dev` is always zero; libthyla-rs pinned the record's size but not the
field's offset; a test comment described a poison the fill had already erased;
the status row claimed sabotage legs nothing had run; and the maps encoding,
which the survey had marked for the operator, was changed without a vote (the
operator ratified it on 2026-10-06). The FILE Burrow's devno copy got the width
pin every other copy has.

**Each copy, proven RED.** Each stored copy of the devno was narrowed back to
32 bits in turn (its `_Static_assert` dropped so it would build) and the suite
booted: `t_stat.devno` with the Image cache entry, the stored mount key, the
cycle check's key, the minter, and the Spoor's own field. Every target test
failed on its named assertion. Narrowing the stored mount key also failed three
older tests on real paths (`devsrv.service_keys_distinct`,
`dev9p.remote_format_ns`, `dev9p.origin_format_ns`): a test boot advances the
minter past 2^32 before them, so every attach after it is a wide-devno witness.
Three older image tests failed beside the image witness only because a failing
test returned with its Burrow refs held, leaving its cache entries live; the
witness now releases before it asserts (4fddeef4d), and the older tests' shape
is queued.
