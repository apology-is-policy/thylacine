V-3b-1c-2a wires the 1c-1 ring ENGINE into the `/srv/warp` SERVER on main
(`4d1a49e3`, hash-fixup `3e12ef12`), so a HOST3D ring becomes a client-mintable
ring flavor under a per-client venus device-ctx -- the tapestryd half of the
client-claimable ring (the weft-share client claim + `warp-prove` cross-Proc are
1c-2b). Holotype CLEAN after fixes (Fable 5, family diversity; 0 P0 / 1 P1 / 1 P2
/ 3 P3, all fixed; GL-verified on thyla-pi KVM/V3D). [[sub-tapestryd]] gains a
"server host3d-ring path" section: `WarpCtx.venus_ctx` (lazy capset-4 ctx, id
`WARP_VENUS_CTX_BASE`+slot -- a disjoint band that the recon's first `+slot`
scheme would have aliased onto `CONV_PROBE_CTX_BASE`, caught by enumerating every
`ctx_create*` id before writing), the `host3d` ring flavor (ADD not replace), the
non-Copy teardown token, the `wring_kick` fail-closed guard, and the boot
self-test.

The entry worth keeping is the three defects, each caught by a DIFFERENT
instrument because the cheaper one was structurally blind to it. **F1 [P1] was the
author's miss**: the self-audit reached the `wctx_finish` leak arm, saw it did not
destroy the venus ctx, and stopped -- reasoning "consistent with dev_ctx, and the
slot is poisoned so the id can't be reused." What it did not trace is the
VINDICATION path, one call away, which un-poisons the recovered slot and destroys
only dev_ctx -- so a wedged-then-recovered slot leaks its venus ctx and the next
client re-mints the same id into a live host context (EEXIST, host3d permanently
lost on that slot). Fable had not watched the author talk itself into "consistent
with dev_ctx," so its context independence closed what family similarity did not.
The generalizable lesson: a self-audit that stops at the boundary of the changed
function misses a bug that lives in the recovery path it never opened -- the
whole-system-stewardship failure mode in miniature.

Two gate-instrument lessons. **The no-boot discriminator tests the VERDICT, not
the CAPTURE**: `test-venus-verdict.sh` was 28/28 against crafted fixtures while the
real venus boot came back UNVERIFIED, because `boot-probe.sh` captured only
`tapestryd: gpu` lines and the self-test lives in `server.rs` with a `warp` prefix
-- the one-word difference invisible to a fixtures-only test, caught only by a
real boot (broadened the filter to `gpu|warp host3d-ring`). And **an assertion is
not an observation** (F4): "teardown OK" was keyed on the sentinel round-trip
alone, so a refused CTX_DESTROY still printed OK -- fixed by reading the poisoned
flag `wctx_finish` sets. F2 [P2] is a disclosure armed one rung ahead: the 1c-1
free-list hands back a reused hostmem extent verbatim, so the ring is zeroed at
install before 1c-2b makes it client-visible.

The venus-ctx client binding and the engine internals remain owned elsewhere
(`sub-kernel-syscall-abi`, `sub-libthyla-rs`, and 1c-1's engine); this change is
the server plumbing over them. GENERALIZES to V-3b-1c-2b and V-3b-2, where venus
submits land and both the leak-arm "venus quiesced by construction" argument and
the kick fail-closed graduate to real venus discipline.
