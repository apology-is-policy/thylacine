# Spec-note coverage

Generated by reading `specs/` directly — do not edit between the markers
(`quaestor render`). The second view whose subject sits outside the vault.

**Why it exists.** A spec note is a TLA+ module's dossier, and per the schema
its body carries the **action-to-site map** — the thing that absorbs
`SPEC-TO-CODE.md` for that module. A reference document that carries such a
map therefore cannot be absorbed until the module has a note to receive it.
`19-handles.md` is the worked case: it looks overdue for stubbing, its
prose is covered by [[sub-kernel-handle]], and what actually blocks it is
that `handles.tla` has no note.

**What it enforces.** The same as [[view-absorption]]: adding or removing a
`.tla` module without re-rendering fails the linter as a stale body, so the
count cannot quietly disagree with the tree. The gap this view reports was
first written down in prose, which is exactly the shape that let the
absorption ledger drift for twenty batches.

**What it does not enforce.** Whether an existing spec note is *complete* —
whether its cfg list matches the module's real configurations, or whether
its action-to-site map still names live functions. A note that has gone
stale against its module still counts as dossiered here.

**Naming.** `specs/foo_bar.tla` is dossiered by `spec-foo-bar`. The
convention is the whole mapping; a module whose note is named otherwise
reads as missing, which is the intended pressure.
