# 145 — The JIT capability (I-42)

**Status: as-built at Clade CL-7k** (`1f0e66c0` kernel, `5633d056` userspace).
Realizes `docs/JIT-ON-WX-DESIGN.md`; the design is pinned by
`docs/LLVM-DESIGN.md` §8 and the invariant by `ARCHITECTURE.md` §28 I-42.

---

## 1. Purpose

Thylacine enforces strict W^X (I-12) and provides **no prot-mutation syscall** —
there is no `mprotect(RW→RX)`, deliberately. A JIT compiler wants to write
machine code and then execute it, which is exactly what that forbids.

The answer is **dual mapping**: the same physical pages reachable at two virtual
addresses, one **RW** (the compiler writes) and one **RX** (the CPU fetches). No
single PTE is ever writable and executable, so I-12 holds at page granularity —
unchanged, not relaxed. Making code executable becomes a deliberate,
capability-gated, region-confined act rather than an ambient one.

This is not a new mechanism. The kernel's own Lazarus W1.5 LSE
alternatives-patcher already self-modifies `.text` through a transient RW-not-X
scratch alias while the canonical mapping stays RO+X, and already performs the
`dc cvau` / `ic ivau` / `dsb` / `isb` publish sequence
(`arch/arm64/mmu.c::mmu_patch_text`). CL-7k exposes that already-trusted
discipline outward, behind a capability.

First consumer: Mesa's llvmpipe shader JIT (CL-7).

## 2. Public API

### Kernel

```c
// kernel/include/thylacine/syscall.h
SYS_JIT_CREATE  = 101,   // (length, out_va) -> 0 / -errno   [CAP_JIT]
SYS_JIT_DESTROY = 102,   // (writer_va)      -> 0 / -errno
SYS_ICACHE_SYNC = 103,   // (vaddr, length)  -> 0 / -errno

struct t_jit_region { u64 writer_va; u64 exec_va; };   // 16 bytes, offsets pinned
#define JIT_REGION_MAX  (64u * 1024u * 1024u)
```

```c
// kernel/include/thylacine/burrow.h
BURROW_TYPE_CODE = 6
struct Burrow *burrow_create_code(size_t size);
```

```c
// kernel/include/thylacine/caps.h
#define CAP_JIT (1ull << 11)     // elevation-only; in CAP_ELEVATION_ONLY
                                 //                 and CAP_GRANTABLE_CLEARANCE
```

### Userspace (`libthyla_rs::jit`)

```rust
let mut r = CodeRegion::new(4096)?;      // needs CAP_JIT
r.write_insn(0, a64::BTI_C);             // landing pad
r.write_insn(4, a64::add(0, 0, 1));
r.write_insn(8, a64::RET);
r.publish();                             // REQUIRED
let f: extern "C" fn(u64, u64) -> u64 = unsafe { r.entry(0) };
```

`Drop` tears down both aliases. `publish_range(off, len)` publishes a patch.

## 3. Implementation

### 3.1 The code Burrow

`BURROW_TYPE_CODE`'s backing is **byte-identical** to `BURROW_TYPE_ANON`: one
eager contiguous `alloc_pages(order, KP_ZERO)` chunk in `pages`/`order`. The
type is not a different allocator — it is a different **admissibility**.

It exists so "this region may carry an RX alias" is a property the *kernel*
mints at creation under `CAP_JIT`, never one a caller asserts at map time. That
is the G-2 WEAVE discipline (a shareable DMA region is minted by
`SYS_DMA_CREATE_WEAVE`, not flagged by its creator) applied to the W^X boundary:
with the property carried by the object, "may I map this executable?" is
answered by a field the caller cannot forge.

Because the backing is identical, the CODE arm of every downstream switch **is**
the ANON arm — `burrow_free_internal`, `burrow_acquire_mapping`'s liveness
check, and `userland_demand_page` all share it. A new gate, not a new lifetime.

`KP_ZERO` is load-bearing rather than hygiene: an executable page handed back
with a previous owner's bytes would be code the Proc can *run* without having
emitted it. All-zero AArch64 decodes as `UDF #0` (permanently undefined), so an
un-emitted page traps instead of executing residue.

Zeroing the memory is only half of that, though, and the missing half was a
CL-7k-3 audit finding (F1). `KP_ZERO` does not touch the **instruction cache**,
and nothing on the free path does either — `burrow_unmap` clears PTEs and
broadcasts TLBI (a *TLB* operation) and `free_pages` performs no cache
maintenance — so a recycled page could still carry I-cache lines from a previous
code region. `sys_jit_create_region` therefore invalidates the I-cache over the
fresh pages before any RX PTE can name them, which is also what every other
executable backing in the tree already did (`kernel/exec.c:121`/`:522`,
`arch/arm64/fault.c:705`/`:876`); the code Burrow had been the sole exception.

### 3.2 Create — one syscall, both aliases

`sys_jit_create_region` installs **both** VMAs under a single `p->vma_lock`
hold:

1. `CAP_JIT` check (first, before argument validation — a capless caller learns
   nothing about which lengths would have been acceptable).
2. `proc_page_charge(p, npages)` — **once** for the region.
3. `burrow_create_code(length)`.
4. `vma_find_gap` + `burrow_map(..., VMA_PROT_RW)` → the writer alias.
5. `vma_find_gap` + `burrow_map(..., VMA_PROT_RX)` → the exec alias.
6. `burrow_unref` — drop the construction handle; the two mappings now own the
   Burrow (`handle_count 0`, `mapping_count 2`).

Splitting create from map would admit a state where an RX alias exists with no
writer, and would put the rollback for a half-installed pair on the caller. Here
either both aliases exist or neither does. It is also the shape the scripture
specifies for the userspace layer: *create → (writer_ptr, exec_ptr)*.

The writer VMA is inserted **before** the second gap search, so `vma_find_gap`
cannot return the range just taken — the two aliases are necessarily disjoint.
In practice they come out **adjacent** (first-fit), which is sound: each VMA
carries its own prot, and a crossing in either direction hits a permission
boundary that faults (writing past the writer's end lands in the read-only exec
alias; executing past the exec alias' end lands in the UXN writer alias).

`sys_jit_create_for_proc` adds only the copy-out, which happens with **no lock
held** — `uaccess` can fault → demand-page → which takes `vma_lock`, so doing it
under the lock would self-deadlock (the REVENANT R-5-F1 rule). On copy-out
failure the region is torn down: the caller never learns where it landed, so it
could never destroy it.

### 3.3 W^X at the PTE

Nothing in this path relaxes a W^X check. Each alias is an ordinary VMA whose
prot `make_user_pte_l3` encodes the ordinary way:

| alias | VMA prot | AP[2:1] | UXN | PXN |
|---|---|---|---|---|
| writer | `VMA_PROT_RW` | `AP_RW_ANY` (writable) | **set** (not executable) | set |
| exec | `VMA_PROT_RX` | `AP_RO_ANY` (not writable) | **clear** (executable) | set |

`vma_alloc` rejects W\|X outright, so the exec alias' prot could never carry a
write bit even by mistake. Both keep PXN: a code region is EL0-executable only;
EL1 never fetches JIT code.

### 3.4 Publish — `SYS_ICACHE_SYNC`

Between a data write and an instruction fetch of the same address the
architecture requires a D-cache clean to PoU plus an I-cache invalidate.
`sys_icache_sync_for_proc`:

1. Validates the range lies within **one alias of one live code region** of the
   caller (either alias — both map the same physical pages).
2. Takes a `burrow_ref` so the pages survive a sibling thread's concurrent
   destroy, then **releases `vma_lock`**.
3. Loops page by page calling `arch_icache_sync_range` on the **kernel direct
   map** alias of each backing page.
4. `burrow_unref` outside the lock. If a sibling destroyed the region meanwhile,
   this is the last reference and frees it here — correct, and the reason the
   ref was taken.

**Cross-PE contract.** `IC IVAU` is Inner-Shareable *broadcast*, so the cache
half is genuinely cross-CPU correct. The trailing `ISB` is not: it retires
prefetched instructions on the **calling** PE only. A peer thread on another CPU
that has already executed at those exec-alias addresses may still hold them
prefetched and is architecturally permitted to run them. Publish makes the bytes
fetchable everywhere; a PE other than the caller must take a
context-synchronization event before branching in — any syscall or exception
return is one, so a thread woken through the kernel is covered, and the exposed
case is a peer spin-waiting on a userspace flag. Nothing at v1.0 drives this,
but ORC's `DualMapMemoryMapper` is emit-on-one-thread / execute-on-a-worker by
nature, so CL-7 must honor the contract or make the syscall broadcast an ISB.

**The cache maintenance runs on the direct map, never the user VA.** That is a
safety property: `dc cvau` / `ic ivau` are memory operations that can take
translation faults, and a user VA is precisely the address a caller can arrange
to be unmapped. It is also architecturally exact — ARMv8 requires data caches to
behave as PIPT, and `IC IVAU` to invalidate every alias of the PA. This is how
Linux's `flush_icache_range` publishes module text written through the linear
map.

### 3.5 Destroy

`sys_jit_destroy_for_proc` takes the **writer VA alone**. The kernel already
knows the pairing (the two VMAs share a Burrow), so taking one name makes it
structurally impossible to destroy half a region or to pass two VAs belonging to
different regions. The peer is found by Burrow identity
(`jit_find_peer_locked`), unambiguous because a CODE Burrow is created with
exactly two mappings and is never cross-Proc shareable (`burrow_share_into`
admits ANON only).

The exec alias is torn down first, so at no instant does an executable view
outlive its writable partner.

### 3.6 Why DESTROY and SYNC are not CAP_JIT-gated

Authority to *create* is the scarce thing. Releasing memory you already own, or
publishing a region you already hold, is not. Gating them would mean a Proc
whose legate scope expired could no longer free the code it had created — a
capability expiry becoming a memory leak — or could no longer finish publishing
a region it legitimately owns. Neither half-state has security value.
`SYS_ICACHE_SYNC`'s range check already requires ownership of a code region,
which is only obtainable by holding `CAP_JIT` at create.

## 4. The capability

`CAP_JIT` is **elevation-only**: excluded from `CAP_ALL`, a member of
`CAP_ELEVATION_ONLY` (so `rfork_internal` strips it from every child), and a
member of `CAP_GRANTABLE_CLEARANCE` (so it is acquirable through a
corvus-mediated, scope- and time-bounded legate, like `CAP_DEBUG`).

That is an invariant obligation, not a style choice: I-42's own text requires
the capability be **non-heritable**, which is exactly what membership in
`CAP_ELEVATION_ONLY` delivers. The consequence is that a clearance is the *only*
path by which any Proc can ever hold it — there is no spawn-time grant.

`usr/corvus` carries a `jit` clearance level whose caps are exactly `CAP_JIT`.

### Scripture-wording note

`JIT-ON-WX-DESIGN.md`, `LLVM-DESIGN.md` §8 and ARCH §28 I-42 each describe
`CAP_JIT` as *"elevation-only, non-rfork-grantable, the `CAP_HW_CREATE` class"*.
The first two properties are what is implemented. The trailing phrase is a loose
analogy meaning "gates a powerful create operation" — **read literally it is
wrong**, because `CAP_HW_CREATE` is fork-grantable (a member of `CAP_ALL`),
which would contradict both "non-rfork-grantable" beside it and I-42's
"non-heritable" clause. Recorded in `caps.h` so a later reader does not "fix"
the bit toward `CAP_ALL` on its strength.

### What it does not confer

`CAP_JIT` controls **who may emit code and where** — a specific Burrow, never
arbitrary process memory. It says nothing about what the emitted code may *do*:
JITed code runs with the Proc's own capability set and namespace, no more. For
untrusted JIT (a browser's JS) the confinement instrument is the namespace, not
this bit. This is JIT-ON-WX caveat #1 restated as policy.

## 5. Tests

`kernel/test/test_jit.c` — 8 tests. The load-bearing one is
`jit.dual_alias_pte_wx_clean`, and it deliberately asserts on the **real L3 page
table entries** rather than on the VMA prots: the prot is what the kernel
*intended*, the PTE is what the MMU will *consult*, and I-12 is a statement
about the latter. Checking prots would pass even if the PTE encoder learned to
set both `AP_RW` and clear `UXN` for a code mapping.

It also asserts both aliases resolve to the **same physical page**. Without
that, "dual map" would be unproven — two mappings of two different pages would
satisfy every permission check and still not be a JIT primitive.

**Revert-probed**: mapping the exec alias `VMA_PROT_RW` instead of `VMA_PROT_RX`
(a direct W^X break) fails the suite 1229/1231 on exactly *"exec PTE is AP_RO
(not writable)"*, and also trips `destroy_rejects_non_writer` — with both
aliases writable, the exec alias starts to look like a writer.

| test | proves |
|---|---|
| `jit.create_requires_cap` | capless refused (`-EACCES`); cap checked before args |
| `jit.create_rejects_bad_args` | length 0 / > `JIT_REGION_MAX`; no charge on reject |
| `jit.dual_alias_pte_wx_clean` | **the invariant**: real PTEs W^X-clean, same PA, both PXN |
| `jit.charges_once_per_region` | I-32: one region, one charge; destroy refunds exactly |
| `jit.destroy_tears_down_both` | no orphaned RX mapping; Burrow freed; 2nd destroy fails clean |
| `jit.destroy_rejects_non_writer` | must name the writer base; refuses a plain anon mapping |
| `jit.icache_sync_gate` | region-confined; no spanning/clipping; refuses non-CODE |
| `jit.write_visible_at_exec_alias` | fresh pages zero (UDF); writer bytes visible at exec |

### In-guest E2E — `/jit-prover` (boot-fatal)

The kernel tests verify the PTEs and the aliasing; they cannot **branch into** a
JITed function. That needs a real EL0 Proc.

The proof is deliberately **one process across the capability boundary** — it is
refused before its clearance redeem and succeeds after, so `CAP_JIT` is the only
variable. Two processes would leave "maybe it was something else about that one"
open.

```
jit-prover: ungated create REFUSED (no CAP_JIT) -- correct
jit-prover: CAP_JIT acquired via the jit clearance
jit-prover: JITed fn(35,100) = 142 -- emitted, published, EXECUTED
jit-prover: re-emitted fn returns 99 -- icache invalidate is live
```

The emitted function is `a + b + 7`, chosen so a wrong answer cannot arise by
accident: `add x0, x0, x1` alone would return the right value from a leftover
`add`, and using both arguments means an entry landing one instruction late
yields a visibly wrong number rather than a plausible one.

The **re-emit** leg is not decoration. A missing icache invalidate shows up
there as "the old function keeps running" — no fault, no crash, just a stale
answer — the failure mode that is easy to miss precisely because nothing looks
wrong.

## 6. Error paths

| return | meaning |
|---|---|
| `-T_E_ACCES` (13) | no `CAP_JIT` (create only) |
| `-T_E_INVAL` (22) | bad length; not the base of a live code region; sync range not contained |
| `-T_E_NOMEM` (12) | page budget, no VA gap, or allocator |
| `-T_E_FAULT` (14) | `out_va` not writable (create only) |

The denial is **`T_E_ACCES`, not `T_E_PERM`**. `errno.h` forbids a handler
returning `-T_E_PERM` because its value (1) collides with the kernel's flat `-1`
generic-failure sentinel, so `libthyla-rs` decodes it as `Io` rather than
`NotPermitted` — a capless caller would be told "I/O error". Same choice
`SYS_CLOCK_SETTIME`'s cap gate makes.

## 7. Known caveats

- **The two aliases are adjacent** in practice (first-fit allocation). Sound —
  every crossing hits a faulting permission boundary — but it means a JIT's own
  off-by-one lands in the sibling alias rather than in unmapped space. A guard
  gap is a possible future hardening, not a correctness requirement.
- **`publish()` is not optional.** Skipping it is not a performance choice: the
  instruction cache may still hold the region's previous contents.
- **BTI.** Emit `a64::BTI_C` as the first instruction of any JITed function
  reached through a function pointer. On BTI-enforcing silicon an indirect
  branch to a non-landing-pad raises a Branch Target exception; elsewhere the
  encoding is a NOP, so emitting it unconditionally costs one instruction and is
  never wrong.
- **`CodeRegion` is `!Send`/`!Sync`** — the raw addresses are meaningful only
  inside the creating Proc's address space.
