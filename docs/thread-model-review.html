Thylacine Thread Model

You asked for a close look at multi-threading for soundness, efficiency and elegance, and for one overhaul plan from both reviewers. This is that plan. A Fable 5.1 reviewer read the kernel independently; aux (Opus 5.5) checked its claims against the code and added its own. Below: the verdict, today's interim fix, every finding, the target design, and the decisions only you can make.

Verdict

The parts that were modelled are sound. The thread lifecycle around them was never designed as a whole, and that is where the defects are.

holds

Sleep, wake and death

Register-then-observe sleeps, the exactly-once last-out, the group death cascade, the on_cpu gates and the tid publish before ready() all hold in the code, as their specs say. Both reviews checked them.

broken

Reclamation is nobody's step

Only the parent's wait_pid freed threads, so a long-lived program filled the 256-thread cap with dead ones. That froze OpenRCT2. The same gap lets execve free an address space while an exiting thread still writes through it.

wrong for real programs

Identity, limits, signals

tids run out into an extinction. A cap of 256 kills a Go program on its 257th M. tkill reaches any thread of the process, and pthread_kill returns ENOSYS.

costly

Hot paths

Every thread create and every free flushes the whole TLB on every CPU. Thread create and exit, across all processes, serialize on one global lock taken with interrupts off.

The documents disagree with the code. proc.h, the I-32 invariant note and IDENTITY-DESIGN call the cap a bound on live threads, while the code counted every thread not yet reaped. That disagreement is how the freeze shipped. ARCHITECTURE 7.3, 7.4, 7.9 and 23.4 describe a thread model that was never built.

Today's interim fix

So your demo does not freeze, an exited thread is now freed at its process's next thread create: proc_reap_exited_threads, which SYS_THREAD_SPAWN, the Linux clone path and a Loom poller setup run before each charges the thread budget. It frees only threads that are EXITING and off every CPU, the same rule wait_pid uses. It claims each one by unlinking it under the process-table lock, keeps the process's CPU time and stack watermark from shrinking, and clears a debugger focus that names it. It landed on aux-3 as e7d6f2f47.

The Fable review's "three holes" in the fix were aimed at the first draft, which also swept at exit. The committed version closes all three: nothing sweeps after the process becomes a zombie, the claim is the unlink under the lock, the kernel process is skipped, and the debug focus is cleared under the lock.

Elegance

  • Two exit functions, one algorithm. exits_term and thread_exit_self both implement the last-out sequence.
  • The Thread carries eleven per-subsystem flags, which turn sleep into a five-way dispatcher. Linux expresses the same space as three sleep classes plus "signal pending".
  • Three trampolines and two user entries, of which only one runs the full return-to-user tail; that gap is F-7.
  • tid and pid are unrelated spaces, so gettid() == getpid() is false for the main thread, which Linux programs assume.
  • A test-only second scheduler (thread_switch) re-implements the switch protocol.
  • The scripture's thread model is not the built one (RFMEM as threads, pthreads over rfork, futex bitsets).

All three reclaim at or after the switch. Thylacine should too, and keep what is its own: the per-process note queue and the modelled death cascade stay the one termination primitive, and thread-directed notes are an addition for pthread_kill and the Linux phenotype, not a replacement.

Target design

Lifecycle

RUNNING ⇄ RUNNABLE/SLEEPING → EXITING → DEAD. EXITING means committed to exit and possibly still on a CPU. DEAD means its last switch-out has completed. A thread is freed exactly once, only when DEAD, by its reaper, or by its joiner for the few kernel threads that have one (the Loom poller). Every thread autoreaps, including the last; wait_pid frees only the process, after its thread count reaches zero.

Where the reaper runs: the one point where the reviews differ

Fable

Per-CPU dead list and reaper

The resume path pushes the dead prev onto a per-CPU list. The idle thread drains it before parking, and a per-CPU reaper kthread drains it on busy CPUs.

Frees run in a context made for them, at the cost of one more kernel thread per CPU and one more queue.

aux

Free inline after the switch

Right after the resume path clears prev->on_cpu and releases the run-queue lock, free prev if it is EXITING, in both resume paths. That is Linux's finish_task_switch. It is legal here because every spinlock raises preempt_count and sched() asserts it is zero, so the resumed thread holds no lock.

No list and no new threads. The cost is one free per thread death on the switch path, which C2's stack cache makes a list push. Stack depth on the interrupt-preempt resume must be measured.

Recommendation: land C2's stack cache first, then the inline free, and measure the stack watermark and switch latency. Fall back to the dead list only if those numbers say so. Either way wait_pid, exec and the debugger stop freeing or holding threads.

Around it

  • Kernel stack cache. A bounded free list of guarded 32 KiB stacks; the guard stays established, so no TLB flush and no zero-fill on the hot path.
  • A per-process thread lock under the process-table lock, for the thread list, the counts and the EXITING commit. The death cascade's "caller holds the table lock" contracts move to it.
  • Exec waits for dead peers (Linux's de_thread): post the die, wake and kick the peers as group termination does, and swap only when the thread count is 1. That closes F-1 by construction.
  • Thread-directed notes: a per-thread pending word beside the process queue, for tkill, tgkill, pthread_kill and thread cancellation.
  • Identity and limits: a 64-bit internal thread id; exhaustion answers EAGAIN, never an extinction; kernel stacks charged to the memory pool; the thread cap raised and made a raisable budget like the page budget.
  • Debug: /proc/<pid>/thread/<tid>/ files; process-level reads report the main thread, not the newest.
  • One first-entry tail for every new thread, so a thread born into a stop parks before its first instruction.
  • torpor: per-bucket locks, first-in first-out wakes, keyed on the address space.
  • Switch fast paths: skip the address-space switch between threads of one process; lazy FP restore only with its own model, otherwise it stays eager.

Invariants and models

  • A new ARCHITECTURE §28 row, Thread reclamation: a thread's context and kstack are freed exactly once, only after its last switch-out completed and only by its reaper or joiner; no address space is destroyed or swapped while a thread of its process is on a CPU; the thread count exceeds the live count by at most the threads between their last switch-out and their free.
  • specs/thread_reap.tla, written before the code, with three buggy configs that must fail: free while on a CPU (the #788 shape), two reapers of one thread, exec before its peers are dead (F-1).
  • Extensions: death_wake.tla (the process is freed only after every thread is reclaimed), caught_target.tla (thread-directed families), and a new torpor.tla for the changed locking.

Decisions for you

Each changes an ABI or scripture, so each needs your vote before its chunk starts. All six were voted on 2026-10-21, each as recommended.

  1. Adopt the Thread reclamation invariant and spec-first for this surface. Recommended: yes; the lifecycle is exactly the kind of mechanism the convictions say must be verified. voted yes
  2. tid policy. (a) never reuse, 64-bit inside, EAGAIN at 231; or (b) reuse per process with a generation, as Linux does. Recommended: (a). It keeps today's property that a stale tid never names another thread. voted (a)
  3. The main thread's tid equals the pid. Recommended: yes; ported programs assume it. voted yes
  4. Thread cap. Raise the default to 4096 and add a spawn permission to raise it, only after kernel stacks are pool-charged. Recommended: yes, in that order. voted yes
  5. Thread-directed tkill/tgkill in the Linux phenotype, and pthread_kill served in Pouch. Recommended: yes. voted yes
  6. The /proc/<pid>/thread/<tid>/ layout, which is operator-visible and goes into the manual. Recommended: yes, with the debugger's focus kept for breakpoints. voted yes

Risks

  • C1 touches every holder of a Thread *. Both reviews enumerated them (the wait_pid walk, the Loom join, the debug focus, the test harness, the scheduler's handoffs, wait lists, the note walk); anything missed is a use-after-free of a recycled slot, so the slot's magic check stays and a freed slot's tid is poisoned.
  • Raising the cap before kernel stacks are pool-charged turns it into a kernel-memory denial of service. C6 lands the charge first.
  • Lazy FP is the one change that can corrupt state silently; it gets its own model or stays eager.
  • Scripture drift is how the freeze shipped; the doc changes are part of each chunk, not a follow-up.
